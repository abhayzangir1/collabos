# Requirements Document

## 1. Application Overview

**Application Name:** CollabOS — Freelance OS

**Description:** CollabOS is a high-end, skill-based peer trading platform that enables professionals to exchange services without monetary transactions. It functions as a Freelance Operating System — a premium SaaS-grade web application featuring a Trust Score Engine v3.4.0, ProofChain portfolio management with a structured skill tagging system (auto-suggestions and domain-based categorization), a real-time SkillSwap marketplace, trade coordination tools with milestone progression, dispute resolution with escalation, team workspaces with RBAC and Kanban-style trade pipeline visualization, analytics with export capabilities (including high-fidelity professional report export and custom skill growth telemetry tracks), a security audit log, and a fully functional i18n-ready OS Knowledge Base with rich structured content. The visual theme is Neubrutalism Dark with custom gold-tinted elevation levels and high-contrast typography. Authentication, database, storage, and real-time capabilities are powered by Supabase.

---

## 2. Users & Use Cases

### Target Users
- Freelancers, independent professionals, and skill-based service providers seeking non-monetary peer collaboration.
- Teams or small collectives managing shared trade pipelines at high volume.

### Core Use Cases
1. A user onboards by selecting or building a professional DNA type, then builds a ProofChain portfolio with structured skill tags (auto-suggested and domain-categorized) and evidence.
2. A user browses the SkillSwap Market, filters by keyword, skill tags, or hours range, proposes a trade with milestones, and tracks sequential milestone progression through the Trade Hub.
3. A user raises a dispute on a specific milestone, blocking completion until resolved; disputes exceeding 7 days display an escalation banner.
4. A workspace owner invites members and manages shared listings and trade pipelines via RBAC; workspace members visualize and manage high-volume service exchange flows using a Kanban-style trade pipeline board.
5. A user switches between Light and Dark (Neubrutalism Dark) themes and language preferences globally.
6. A user exports analytics data as PDF, CSV, or JSON, or as a high-fidelity professional report including chart visualizations.
7. A user configures custom telemetry tracks on the Analytics page to monitor specific skill growth vectors.
8. A user reads structured Knowledge Base articles covering platform features, the Trust Algorithm, and use case walkthroughs, with all content rendering correctly in their selected language.

### 3.3 Protected Routes

#### /dashboard — Main Dashboard (4-Zone Layout)

**Zone A — KPI Summary Bar**
- Displays real-time count-up animated counters for: Total Proofs, Active Trades, Trust Score.
- Values update in real time via Supabase Realtime subscription.
- The Supabase Realtime subscription for the dashboard KPI bar subscribes to changes on the relevant user records (proofs table, trades table, trust_score_history table) and updates counter values without page refresh.
- Counter labels and values are constrained to their cells; long values are formatted (e.g., abbreviated with k/M suffix) to prevent overflow.

**Zone B — Contextual Primary Action**
- Contextual primary CTA based on user state:
  - Zero trades → Browse Market button.
  - Active trade with pending milestone → Complete Milestone button linking to the relevant trade.
- If no actionable state exists, displays a Professional Empty State: an illustration with an actionable prompt (e.g., Start by adding your first Proof).
- CTA labels and prompt text wrap within their containers; no text overflow permitted.

**Zone C — Real-time Activity Feed & Quick Actions**
- Left column: Real-time Activity Feed — chronological list of events (trade proposals received, milestone confirmations, endorsements, dispute updates). Powered by Supabase Realtime.
  - The Activity Feed subscribes to a dedicated notifications or activity_feed table in Supabase; new rows inserted by backend triggers are broadcast to the relevant user's subscription channel and prepended to the feed list without page refresh.
  - Each feed entry displays: event type icon, descriptive text, and relative timestamp.
- Right column: Quick Actions — shortcut buttons to: Add Proof, Browse Market, Create Listing, Invite to Workspace.
- Activity feed entries truncate long mononyms or event descriptions with an ellipsis and expose the full text via tooltip; no text may overflow its row container.

**Zone D — Persistent Sidebar**
- Desktop: Side-rail navigation with icon + label links to all main sections. Unread badge counts on Trades and relevant notifications.
- Mobile: Bottom navigation bar with the same links and badge counts.
- Navigation labels truncate gracefully if the sidebar is in a collapsed state; badge count numerals are capped at display 99+ to prevent badge overflow.

**Backend Requirements for Dashboard**
- Supabase Realtime channels must be correctly configured for the authenticated user on page mount: one channel for KPI counters (subscribing to INSERT/UPDATE on proofs, trades, trust_score_history filtered by user_id), one channel for the Activity Feed (subscribing to INSERT on activity_feed filtered by recipient_user_id).
- Channels must be unsubscribed and cleaned up on component unmount to prevent memory leaks and duplicate event delivery.
- The backend must insert activity_feed rows for all qualifying events: trade proposal received, milestone marked complete by counterparty, dispute opened or updated, endorsement received, workspace invitation accepted.
- Badge counts are derived from unread activity_feed rows; marking a section as visited triggers a backend update to mark relevant rows as read.

#### /proofchain — ProofChain Portfolio Manager

- Displays all user proofs in a grid/list view toggle.
- Each proof card shows: title, description, skill tags (with domain category label), value indicator, media/link, verification status (Verified — Locked / Unverified), and a pinned badge if the proof is currently pinned.
- **Text overflow rules for proof cards:** Title is clamped to 2 lines with ellipsis overflow. Description is clamped to 3 lines with ellipsis overflow. Skill tag chips that exceed the card width wrap to a second row; if more than one row of tags would be needed, remaining tags are collapsed behind a +N more indicator.
- **Verified / Locked status:** Proofs confirmed by a counterparty in a completed trade are marked Locked and cannot be edited.
- **Add Proof:** Form with title, description, skill tags (see Structured Skill Tagging System below), value, optional file upload (stored in Supabase Storage, accessed via signed URLs), and optional external link.
- **Edit Proof:** Available only on Unverified (unlocked) proofs. Locked proofs display a read-only view.
- **Delete Proof:** Available only on Unverified (unlocked) proofs. A confirmation dialog is shown before deletion. Deleting a pinned proof automatically removes it from the pinned set.
- **Bulk Actions:**
  - Select All toggle.
  - Bulk Pin: User may pin up to 3 proofs to their public profile simultaneously. Attempting to pin a 4th prompts selection of which existing pinned proof to replace.
  - Bulk Export to PDF: User selects multiple proofs and exports them as a single PDF document.
- Professional Empty State shown when no proofs exist.

**Structured Skill Tagging System**
- Skill tags in ProofChain are organized under a domain-based categorization structure.
- Predefined top-level domains include categories such as: Engineering, Design, Marketing, Writing, Data & Analytics, Operations, Legal & Finance, and Others. Each domain contains a curated set of sub-tags.
- When a user types in the skill tag input field, the system provides real-time auto-suggestions drawn from the predefined tag library, filtered by the characters entered.
  - Suggestions are displayed in a dropdown list grouped by domain.
  - The user may select a suggested tag or type a custom tag not present in the library.
  - Custom tags are accepted as free-text entries and are not assigned to a predefined domain; they are displayed with a Custom domain label.
- Each tag on a proof card displays its domain category as a secondary label (e.g., Engineering · React, Design · Figma).
- The skill tag input on the Add Proof and Edit Proof forms supports adding multiple tags per proof.
- The same structured tagging system and auto-suggestion behavior applies wherever skill tags are entered across the platform (e.g., Create Listing in the SkillSwap Market, Custom Telemetry Track configuration in Analytics).

**Backend Requirements for ProofChain**
- All proof CRUD operations (create, read, update, delete) are performed via Supabase with RLS policies ensuring users can only access their own proof records.
- File uploads for proof media are stored in a dedicated Supabase Storage bucket (e.g., proof-media); the backend generates a signed URL upon each read request, scoped to the authenticated user.
- The locked status of a proof is set by a backend trigger or function when a trade reaches Completed state; the trigger identifies all proofs referenced in the completed trade and sets their is_locked flag to true.
- The pinned_proofs field is stored as an array of proof IDs on the user record (maximum 3 entries); updates are validated server-side to enforce the 3-pin limit.
- Bulk PDF export is generated client-side from the selected proof data already loaded in the frontend; no separate backend endpoint is required for PDF generation.
- The predefined skill tag library is stored in a read-only Supabase table (skill_tags) with columns: id, domain, label; users cannot insert, update, or delete rows in this table (RLS: SELECT only for authenticated users).

#### /market — SkillSwap Market

- Displays all active skill listings from all users.
- **Search & Filter:**
  - Real-time search by skill keyword.
  - Filter by skill tags (with domain-grouped tag picker consistent with the structured tagging system).
  - Filter by hours range.
- Each listing card shows: user mononym, DNA type, skill offered, skill requested in exchange, Trust Score.
- **Text overflow rules for listing cards:** Mononym is truncated with ellipsis if it exceeds the allocated width. Skill offered and skill requested labels are each clamped to 1 line with ellipsis overflow. Trust Score value is formatted to prevent numeric overflow.
- **Listing Detail View:** Clicking a listing card opens a detail panel or modal showing full listing description, the lister's pinned proofs (up to 3), and the Propose Trade CTA. All text within the detail panel wraps correctly; no overflow permitted.
- **Propose Trade flow:**
  - User selects a listing and clicks Propose Trade.
  - Multi-step form:
    - Step 1: Confirm skills being exchanged.
    - Step 2: Milestone Toggle. If enabled, proposer defines 2–5 milestones, each with a Title, Description, and Date.
    - Step 3: Review and submit.
  - System blocks a user from proposing a trade with themselves at the API/backend level.
- **Incoming Trade Proposals:** Users receive trade proposals from other users. Proposals appear in the Activity Feed on the dashboard and are accessible from the Trade Hub. The recipient may Accept or Decline a proposal.
  - On Accept: a trade record is created and both parties are redirected or linked to /trades/[id].
  - On Decline: the proposal is marked declined; the proposer sees a declined status on their trade entry.
- **Create Listing:** Authenticated users may create a listing specifying skill offered and skill requested, using the structured skill tagging system with auto-suggestions.
- **Edit Listing:** Users may edit their own listings from the Market page or from their listing card. Editing is available for both active and deactivated listings owned by the current user.
- **Deactivate Listing:** Users may deactivate their own listings, removing them from the public marketplace view while retaining the listing record.
- **Delete Listing (Permanent):** Users may permanently delete their own listings. A confirmation dialog is shown before deletion. Once deleted, the listing record is removed and cannot be recovered. Listings that are currently referenced by an active or proposed trade cannot be deleted until the trade reaches a terminal state (Completed or Declined).
- Professional Empty State shown when no listings exist.

**Backend Requirements for SkillSwap Market**
- The listings table has RLS policies: SELECT is open to all authenticated users for active listings; INSERT, UPDATE, DELETE are restricted to the listing owner.
- The self-trade block is enforced at the database level via a CHECK constraint or a Supabase Edge Function that validates proposer_user_id ≠ listing_owner_user_id before inserting a trade proposal record.
- Trade proposal creation inserts a row into the trades table (status: Proposed) and simultaneously inserts an activity_feed row for the listing owner (recipient) notifying them of the new proposal.
- Listing deletion is blocked by a database-level constraint or Edge Function that checks for any trades referencing the listing_id with status IN (Proposed, Active) before allowing DELETE.
- The hours_range field on listings is stored as a numeric value or range type; the filter query uses a WHERE clause with the user-selected min/max bounds.
- Skill tag filtering on the market uses a contains or overlap query against the skill_tags array column on the listings table.

#### /trades — Trade Hub (Command Center)

- Lists all active and completed trades for the current user, including incoming proposals awaiting response.
- Each trade entry shows: counterparty mononym, trade status (Proposed / Active / Completed / Declined / Disputed), current milestone, last activity timestamp.
- **Text overflow rules for trade entries:** Counterparty mononym is truncated with ellipsis if it exceeds the allocated column width. Status badges use fixed-width chips. Timestamp values are formatted to a consistent short date-time string that fits within its column.
- Tabs or filter controls to switch between: All, Active, Completed, Proposed (incoming), Declined.
- Professional Empty State shown when no trades exist.

#### /trades/[id] — Individual Trade Detail

**Trade Header**
- Displays: trade status badge, counterparty mononym and DNA type, date created, and overall trade progress (e.g., 2 of 4 milestones completed).
- Mononym and DNA type truncate with ellipsis if the header container is too narrow; full values are exposed via tooltip.

**Milestone Stepper**
- Displays sequential milestones (2–5) defined at trade creation.
- Each milestone has a status: Pending → In Progress → Awaiting Confirmation → Completed.
- Sequential enforcement: Milestone N must be fully completed before Milestone N+1 becomes active.
- Dual-confirmation: both parties must independently mark a milestone complete before it advances.
- Mark Complete action is blocked if an open dispute exists on that milestone.
- When all milestones reach Completed status, the trade is automatically marked Completed and the Trust Score Engine recalculates scores for both parties.
- Milestone titles are clamped to 1 line with ellipsis overflow within the stepper component; full title is visible in the expanded milestone detail view.

**Evidence Journal**
- Drag-and-drop interface for submitting files or links as evidence, with a progress bar displayed during upload.
- Each submission is scoped to a specific milestone via a Milestone Scope selector dropdown.
- Uploaded files stored in Supabase Storage; accessible only to the two trade parties via time-limited signed URLs.
- Evidence entries are listed chronologically per milestone, showing submitter mononym, file name or link, and submission timestamp.
- File names that exceed the display width are truncated with ellipsis; full file name is shown on hover via tooltip.

**Chat**
- Real-time messaging between the two trade parties using Supabase Realtime and Presence.
- Features: typing indicators (Partner is typing...), read receipts (Seen), 6-emoji reactions on messages.
- Message history persisted in the database.
- Messages are paginated; older messages load on scroll-up.
- Message bubbles wrap long text content within the chat container width; no horizontal overflow permitted. URLs within messages are wrapped using word-break rules.

**Dispute Panel**
- User may open a dispute scoped to a specific milestone.
- Opening a dispute requires a mandatory reason field (minimum 20 characters).
- While a dispute is open on a milestone, the Mark Complete action for that milestone is blocked for both parties.
- Dispute states: Open → Under Review → Resolved.
- A dedicated, formatted comment thread is available within the dispute for resolution notes; both trade parties may post comments.
- If a dispute remains in Open or Under Review state for more than 7 days, an Under Review escalation banner is displayed prominently on the trade detail page.
- Dispute resolution is manual (admin or mutual agreement); resolution unblocks the milestone.
- Resolved disputes display a read-only summary with the resolution note.
- All text within the dispute panel (reason field, comment thread, resolution note) wraps within its container; no overflow permitted.

**Backend Requirements for Trade Hub**
- The trades table has RLS policies ensuring only the two trade parties (proposer_user_id, recipient_user_id) can read or write the trade record.
- Milestone state transitions are enforced by a Supabase Edge Function or database trigger: the function validates sequential order (milestone N-1 must be Completed before milestone N can move to In Progress), validates dual-confirmation (both party_a_confirmed and party_b_confirmed flags must be true before a milestone advances to Completed), and validates that no open dispute exists on the milestone before allowing a Mark Complete action.
- When all milestones on a trade reach Completed status, a database trigger automatically updates the trade status to Completed and invokes the Trust Score Engine recalculation function for both parties simultaneously.
- The Trust Score Engine recalculation function: reads the current counts of completed trades, verified proofs, unverified proofs, and endorsements for the user; computes the new score using the formula; inserts a row into trust_score_history with new_score, delta, event_type, and timestamp; updates the current_trust_score field on the user record.
- Evidence file uploads use Supabase Storage with a dedicated bucket (e.g., trade-evidence); the bucket has RLS policies restricting access to the two trade parties of the relevant trade. Signed URLs are generated server-side with a configurable expiry (e.g., 1 hour) and returned to the client on each read request.
- The chat messages table has RLS policies restricting read and write to the two trade parties. Supabase Realtime is configured to broadcast INSERT events on the messages table to a channel scoped to the trade ID. Presence is used to track which party is currently viewing the chat, enabling typing indicators and read receipts. Read receipts are updated by a backend call when the recipient's Presence indicates they are active in the chat and a new message arrives.
- Disputes are stored in a disputes table with columns: id, trade_id, milestone_id, opened_by_user_id, reason, status, opened_at, resolved_at, resolution_note. A scheduled Supabase function or cron job checks for disputes where status IN (Open, Under Review) and opened_at < NOW() - INTERVAL 7 days, and sets a flag (escalated: true) on those rows; the frontend reads this flag to display the escalation banner.
- The Dispute Panel is loaded via code-splitting (lazy loading) as a separate chunk within the /trades/[id] route.

#### /analytics — Analytics Page

- **Real Data Only:** Charts and metrics only render when real data is present. If no data exists, displays No data available — no illustrative or placeholder charts are shown.
- **Date Range Filter:** User may filter analytics data by a custom date range (default: last 30 days).
- **Charts displayed when data is available:**
  - Trust Score trend over time (line chart sourced from trust_score_history).
  - Skill Category breakdown (pie or bar chart of skill tags across completed trades, grouped by domain category).
  - Hourly Exchange Balance (bar chart of hours offered vs. hours received).
- **Summary Metrics Panel:** Displays aggregate figures: Total Trades Completed, Total Proofs Added, Total Endorsements Received, Current Trust Score.
- Chart axis labels, legend labels, and tooltip text are constrained to their allocated space; long skill tag names in chart legends are truncated with ellipsis and shown in full on hover.
- **Custom Skill Growth Telemetry Tracks:**
  - Users may define and manage custom telemetry tracks to monitor specific skill growth vectors.
  - Each track is defined by: a Track Name, one or more target Skill Tags (selected via the structured tagging system with auto-suggestions and domain grouping) to monitor, and a Metric Type (e.g., trade frequency, proof additions, or hours exchanged for the selected skill tags).
  - Configured tracks are displayed as individual chart panels on the Analytics page, each rendering a time-series line chart scoped to the track's defined skill tags and metric type.
  - Users may add, edit, or delete their own custom tracks. A maximum of 5 custom tracks may be active simultaneously.
  - Custom track panels respect the active Date Range Filter.
  - If a custom track has no data within the selected date range, the panel displays No data available for this track.
  - Track Name and Skill Tag labels within track panels are truncated with ellipsis if they exceed the panel width; full values shown on hover.

**Backend Requirements for Analytics**

## 4. Business Rules & Logic

### Trust Score Engine v3.4.0
- Calculated and recalculated by a backend function upon relevant events (trade completion, proof verification, endorsement received).
- Formula:
  - Trust Score = (Trades Completed × 10) + (Verified Proofs × 8) + (Unverified Proofs × 3) + (Endorsements × 2)
- Every recalculation logs a record to the trust_score_history table containing: user ID, new score, delta (e.g., +10), event type, and timestamp.
- Score history is available for display in Analytics.
- Both parties in a completed trade receive a Trust Score recalculation event simultaneously upon trade completion.

### Trade Lifecycle
- A trade begins in Proposed state when a proposer submits a trade proposal.
- The recipient may Accept (moves trade to Active) or Decline (moves trade to Declined).
- An Active trade progresses through milestones sequentially.
- When all milestones are Completed, the trade moves to Completed state and Trust Score recalculation is triggered for both parties.
- A Declined trade is immutable; no further actions are possible.

### Listing Deletion Rules
- A user may permanently delete their own listings via a confirmation dialog.
- A listing that is currently referenced by a trade in Proposed or Active state cannot be deleted; the delete action is blocked with an inline message explaining that the listing is linked to an active trade.
- Once a trade reaches a terminal state (Completed or Declined), the associated listing becomes eligible for deletion.
- Permanent deletion removes the listing record entirely and cannot be undone.

### Theme Availability
- The application supports exactly two themes: Light Mode and Neubrutalism Dark Mode.
- The themes Neumorphism Light, Neumorphism Dark, Material Dark, and Neubrutalism Light are permanently removed from the system. No references to these themes may exist in the UI, settings, database, or CSS.

### Global Text Overflow Prevention
- All text elements across the entire application must be constrained to their layout containers. The following rules apply globally:
  - Single-line text fields (headings, labels, mononyms, status badges, timestamps): truncate with ellipsis (text-overflow: ellipsis) when content exceeds the container width.
  - Multi-line text blocks (descriptions, messages, notes): use line-clamp where a maximum line count is defined; otherwise wrap with word-break rules that prevent horizontal overflow.
  - URLs and long unbreakable strings: apply word-break: break-all or overflow-wrap: anywhere to prevent horizontal scroll.
  - Chip/tag collections: wrap to a defined maximum number of rows; excess items are collapsed behind a +N more indicator.
  - Table and list cells: all cell content wraps or truncates within column boundaries; no cell may cause horizontal scroll on its row.
  - Tooltips: full content is exposed via tooltip on hover for any element that truncates or collapses content.
  - No section, page, card, modal, panel, or component anywhere in the application may exhibit unintended horizontal text overflow.

### Row Level Security (RLS)
- Every Supabase table has RLS enabled.
- Users may only read/write their own records, shared trade records (scoped to both parties), or workspace records they have role-based access to.
- A user cannot see a trade unless they are a direct participant or a member of the associated workspace.

### Security Audit Log
- Sensitive events are logged to a dedicated audit log table: Password Change, Failed Login attempts, and Unauthorized Access attempts.
- Log entries include: user ID (if resolvable), event type, timestamp, and relevant metadata.

### Session Invalidation
- All active sessions are invalidated upon: password reset, email change, or manual Sign Out All action.

### Signed URLs for Evidence
- Files uploaded to Supabase Storage as trade evidence are only accessible via time-limited signed URLs.
- Signed URLs are scoped to the two parties in the relevant trade.

### Self-Trade Block
- The system prevents a user from proposing a trade with themselves at the API/backend level.

### Unverified User Redirect
- Any unverified user attempting to access a protected route is redirected to /verify-email.

### Dispute Block & Escalation
- While a dispute is open on a milestone, neither party may mark that milestone as complete.
- If a dispute remains unresolved for more than 7 days, an Under Review escalation banner is shown on the trade detail page.

### Milestone Sequential Enforcement
- Milestone N must reach Completed status before Milestone N+1 becomes active.

### Workspace Invitation Expiry
- Invitation links expire exactly 7 days after generation. Expired links return an error and cannot be used to join.

### Mononym Support
- The display name field accepts a single name with no surname requirement throughout the entire system.

### Real-time Performance
- All real-time events (Activity Feed, Chat, KPI updates, Workspace Kanban board) use Supabase Broadcast/Presence targeting sub-100ms latency.

### Notification State
- Unread badge counts on the sidebar/bottom nav for Trades are incremented when: a new trade proposal is received, a milestone is marked complete by the counterparty, a dispute is opened or updated, or a workspace invitation is accepted.
- Badge counts are cleared when the user visits the relevant section.

### Code-Splitting for Non-Critical Modules
- All non-critical protocol modules are loaded via code-splitting (lazy loading) to optimize initial load performance.
- Non-critical modules include: /analytics (including all chart panels and custom telemetry track panels), /proofchain, /workspaces and /workspaces/[id], /knowledge-base, and the Dispute Panel within /trades/[id].
- Critical modules loaded eagerly (not split): /login, /register, /verify-email, /dashboard, and the core Trade Hub shell at /trades and /trades/[id] (excluding the Dispute Panel).
- Each lazily loaded module displays a lightweight loading indicator while the module chunk is being fetched.
- Code-splitting boundaries are enforced at the route level; sub-components within a lazy-loaded route are bundled within that route's chunk.

### Custom Telemetry Track Rules
- A user may define up to 5 active custom telemetry tracks simultaneously.
- Each track requires a Track Name, at least one Skill Tag, and a Metric Type.
- Track data is computed from the user's own trade and proof history scoped to the selected skill tags.
- Custom track data is stored per user and persists across sessions.
- Deleting a custom track removes its panel from the Analytics page and its stored configuration; historical source data is not affected.

### High-Fidelity Professional Report Export Rules
- The professional report export is only available when at least one chart has renderable data within the selected date range.
- Charts with no data in the selected range are omitted from the report with a per-section no data note.
- The report PDF layout is fixed: cover section → Trust Score trend chart → Skill Category breakdown chart → Hourly Exchange Balance chart → active custom telemetry track charts (in user-defined order) → Summary Metrics Panel.
- The export is triggered from the Analytics page and respects the active date range filter at the moment of export.

### Structured Skill Tagging Rules
- The predefined tag library is the authoritative source for auto-suggestions; it is read-only and cannot be modified by users.
- Auto-suggestions are triggered after the user types at least 1 character in a skill tag input field.
- A maximum of 10 skill tags may be added per proof entry.
- Custom (free-text) tags that do not match any predefined tag are stored as-is and labeled with a Custom domain indicator.
- Domain-based grouping is applied consistently wherever skill tags are displayed or filtered across the platform.

### Kanban Trade Pipeline Rules
- The Kanban board is scoped to the individual workspace; it displays only trades associated with that workspace.
- Real-time updates to trade status and milestone progress are reflected on the Kanban board without page refresh via Supabase Realtime.
- Drag-and-drop between Proposed and Active columns is permitted only for Admin and Owner roles; Member role users have a read-only view of the Kanban board.
- Dragging a card from Proposed to Active is equivalent to accepting the trade proposal and follows the same trade lifecycle transition rules.
- All other column transitions are system-driven and cannot be triggered by drag-and-drop.
- The Kanban board view state (column scroll position, selected filters) is not persisted across sessions.

### Neubrutalism Dark Theme Rules
- Gold-tinted elevation tokens (Elevation 1, 2, 3) are applied consistently to all surface layers across the application when Dark Mode is active.
- High-contrast typography tokens (primary white, secondary warm off-white, gold accent) are applied globally in Dark Mode via CSS variables.
- The gold accent color (#C9A84C) is used exclusively for interactive element labels, borders, and focus rings in Dark Mode; it must not be used as a background fill for large surface areas.
- All elevation and typography CSS variables are toggled atomically with the Dark Mode theme switch; no partial application is permitted.

### Knowledge Base Content & i18n Rules
- All Knowledge Base article content (headings, body text, code-style references, table content) is stored as i18n-keyed strings; no hardcoded English strings may appear in the Knowledge Base rendering layer.
- Switching language in Settings triggers an immediate re-render of all Knowledge Base content in the selected language without page reload.
- The Knowledge Base search index is rebuilt or re-queried in the active language when the language changes.
- Article content is read-only; no user can create, edit, or delete Knowledge Base articles via the UI.
- The sidebar navigation, breadcrumb trail, and search results all update to the selected language simultaneously with the article content.

### Frontend–Backend Integration Correctness Rules
- Every protected route must validate the authenticated session on mount via Supabase Auth; if the session is absent or expired, the user is redirected to /login.
- Every Supabase Realtime subscription must be established after session validation and torn down on component unmount.
- All data-fetching hooks must handle loading, success, and error states explicitly; no component may render in an indeterminate state without a loading indicator or error boundary.
- All form submissions that write to the database must display an inline loading state on the submit button and an inline success or error message upon completion.
- All Supabase Edge Functions and database triggers must return structured error responses; the frontend must surface these errors as inline messages rather than silent failures.
- All file upload operations must validate file type and size client-side before initiating the Supabase Storage upload; server-side storage policies must enforce the same constraints.

- The Knowledge Base sidebar navigation, breadcrumb trail, and search bar function correctly; search returns matching articles with title and excerpt; clicking a result navigates to the correct article.
- All Knowledge Base article content re-renders instantly in the selected language when the language is changed in Settings.
- User can update mononym, email (with re-verification), and DNA type from Settings.
- Password reset and Sign Out All invalidate all active sessions; password changes are logged to the Security Audit Log.
- All active sessions are visible in Settings with device label and last active timestamp.
- Workspace creation, member invitation, role management, and member removal function correctly per RBAC rules; all operations are enforced by RLS policies.
- Workspace invitation links expire after 7 days and are rejected thereafter; active links can be revoked by Owner or Admin.
- Workspace deletion removes all associated data and revokes all member access via cascade.
- RBAC is enforced: Owners have full control, Admins manage members and listings, Members can only view and contribute.
- The Workspace Shared Trade Pipeline supports toggling between List View and Kanban View; the selected mode persists per workspace per user session.

## 7. Out of Scope (This Release)

- Monetary payments or escrow functionality.
- Native mobile applications (iOS / Android).
- Admin dashboard for platform-level dispute resolution.
- Automated dispute resolution logic.
- Third-party OAuth login (e.g., Google, GitHub).
- Email notification system (beyond verification and password reset).
- Public user profile pages accessible by URL.
- Endorsement submission UI (Trust Score formula includes endorsements, but the mechanism for submitting endorsements is deferred).
- Advanced analytics (cohort analysis beyond current export scope).
- Workspace billing or subscription tiers.
- Account deletion flow.
- Push notifications or in-app notification centre beyond badge counts.
- User-editable or community-contributed additions to the predefined skill tag library.
- Kanban board view state persistence across sessions.
- Server-side rendering or static site generation for the Knowledge Base.
- Knowledge Base article authoring or CMS interface.
